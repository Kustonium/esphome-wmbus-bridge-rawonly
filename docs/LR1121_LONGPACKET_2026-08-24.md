## 1. The question

wM-Bus T1 applies 3-out-of-6 encoding, so a frame occupies 1.5x its decoded
size on air. Measured on this project's own hardware, real frames reach
**435 raw bytes** (256 decoded). A concrete field example captured on a foreign
setup on 2026-08-23: an Elgama Gama 350 electricity meter, `L=0xBE` (191-byte
frame, 217 bytes with DLL CRCs), **326 raw bytes on air**.

The LR1121 receive path currently caps at 255 raw bytes. That is roughly 170
bytes with CRCs, i.e. frames up to about `L=0x97`. Most meters fit. The long
ones do not.

C-mode is unaffected: no 3-of-6 expansion, so 255 on air is 255 frame bytes.

**Can the LR1121 receive more than 255 raw bytes in one burst?**

---

## 2. Why the SX1262 trick does not port

`transceiver_sx1262.cpp` implements Semtech AN1200.53. It rests on two
published SX126x registers:

| Register | Address | Role |
|---|---|---|
| `REG_RX_ADDR_PTR` | `0x0803` | current HW write pointer into the 256-byte buffer, readable **during** reception |
| `REG_RXTX_PAYLOAD_LEN` | `0x06BB` | intended end index; writing `current_index - 1` on every poll stops the radio ever finishing the packet |

Read the pointer, drain what arrived, push the end forward, repeat. Both halves
are required, and both are documented.

The LR1121 publishes neither.

### Evidence (LR1121 UM Rev 2.2 + SWDR001-2.4.1)

**§8.10 Data Buffer** — two 255-byte RAM buffers, one RX one TX, and:

> The LR1121 automatically controls the data pointers, which means that no base
> address handling by the user is necessary.

There is no `SetBufferBaseAddress` equivalent anywhere in the 47-function
`lr11xx_radio.h` API. The only window into the buffer is:

```c
lr11xx_radio_get_rx_buffer_status(context, &st);
    st.pld_len_in_bytes      // uint8_t
    st.buffer_start_pointer  // uint8_t
```

and the UM describes it as the pointer to the first byte of **the last packet
received** — i.e. after `RX_DONE`, not during. Nothing to poll mid-frame.

`ReadBuffer8(Offset(7:0), Len(7:0))` — both fields 8-bit, so even if the data
existed there is no way to address past 255. `pld_len_in_bytes` in
`SetPacketParams` is likewise `uint8_t`, in both fixed- and variable-length
header modes.

### Documentation trap

**Chapter 10 of the same UM contradicts §8.10.** It describes a shared buffer
with a user-defined `RxBaseAddr`, and states that an oversized RX packet
overwrites the TX portion. That is SX126x text that was not updated for this
part: no LR11xx command implements it. Do not build on chapter 10.

## 3. The one remaining opening

`SWDR001-2.4.1` exposes arbitrary memory access with a **32-bit** address:

```c
lr11xx_regmem_read_regmem32 (context, address /* uint32_t */, buffer, len /* <=64 words */);
lr11xx_regmem_read_mem8     (context, address /* uint32_t */, buffer, len);
```

If the internal write pointer lives at some address, it can be polled the same
way `0x0803` is on the SX126x. The address is not published — but it is
*observable*, because a write pointer is the one register whose value tracks
incoming bytes.

### Anchors for the scan region

Real peripheral addresses leak out of the SDK and UM:

| Address | Where it appears |
|---|---|
| `0x00F30054` | `lr11xx_radio_apply_high_acp_workaround()` |
| `0x00F20214` | BLE beaconning compatibility (twice, incl. RX gain step) |
| `0x00F20230` | BLE beaconning compatibility |

So start at **`0x00F20000`–`0x00F30400`**. That is ~1280 words, and
`ReadRegMem32` takes 64 words (256 bytes) per transaction, so a full sweep is
~20 transactions — on the order of 10–20 ms at 8 MHz SPI.

## 4. Experiment 1 — does the buffer wrap, or does RX stop at 255?

**Do this one first. It can close the question in half an hour, and it decides
whether the pointer even matters.**

If the packet engine *stops* at 255, there is nothing to stream and the answer
is final. If it *wraps* (the UM's `ReadBuffer8` text says "RX buffer must be
implemented as a ring buffer"), then the situation is better than on the
SX1262: only the pointer is missing, because draining fast enough is sufficient
on its own — no writable packet-end register needed.

### Method

Transmit ~400 bytes with a **position-identifiable** payload — byte *n* =
`n & 0xFF` — from the SX1276 workshop transmitter. Do not use a real telegram;
the point is to read positions off the buffer directly. After reception, read
the whole buffer with `ReadBuffer8(0, 255)`.

| Observation | Conclusion |
|---|---|
| `00 01 02 ... FE` | engine stopped at 255. **Question closed.** |
| a backwards jump mid-buffer, e.g. `... 8F 90 00 01 02 ...` | it wraps. Proceed to Experiment 2. |

## 5. Experiment 2 — locate the write pointer

Only if Experiment 1 shows wrapping.

### Method

Transmit a deliberately long frame (the SX1276 in unlimited-packet mode can
send far more than 435 bytes; 2000 bytes at 100 kb/s is a 160 ms window).
Sweep the region twice during a single transmission and diff.

### A candidate must satisfy ALL FOUR

1. increases monotonically **only** while a frame is being received
2. is static when the transmitter is silent
3. **advances with byte count, not with elapsed time** — send the same byte
   count at two different bitrates; the increment must be identical
4. after a frame of known length N, the increment is exactly N modulo 256

Condition 3 is the important one. It eliminates every RTC and free-running
timer in one step, and skipping it is how a plausible-looking wrong address
gets adopted.

## 6. Firmware pinning — why "undocumented" is manageable here

The radio firmware is a **versioned artefact under our control**, not an
environment variable. `Dokumentacja ESP/LR1121/radio_firmware_images-master/
lr1121/transceiver/` holds `0101`, `0102`, `0103`, `0104` as `.bin` and as C
arrays, and `SWTL001-2.3.0` flashes them.

Therefore:

* Pin one version, verify the address on it, and **gate on `GetVersion`**:

```
if (fw_version != <verified>) {
    long-packet path OFF;
    ESP_LOGW(TAG, "RX write pointer verified only for FW 0x%04X, found 0x%04X "
                  "- long-packet path disabled", VERIFIED_FW, fw_version);
}
```

  A silent failure becomes a stated one. This is the whole point.

* Free control experiment: re-verify the address on the other three images. If
  it holds across all four, it is likely a hardware peripheral address rather
  than a firmware artefact. If it moves, that is immediately known and gated.

## 7. Ground rules

* **Behind a config flag, default off**, like the QDS path. This is bench work
  built on an undocumented address; it does not go in the main receive path
  without an explicit opt-in and a loud log line.
* **Failures must be audible.** Same principle the driver already applies to
  `tcxo_voltage`: prefer the option that fails loudly over the one that works
  today and drifts later.
* **Both outcomes are publishable.** Either long packets on an LR1121 — which
  nobody has — or "the engine stops at 255, the write pointer is inaccessible,
  verified as follows" — which nobody has written down either. The negative
  result saves the next person a week, and it is the only information that will
  exist on this topic.
* Anyone reading this later: the driver header still cites datasheet Rev 2.1.
  Rev 2.1 datasheet and UM Rev 2.2 are both in `Dokumentacja ESP/LR1121/`.
